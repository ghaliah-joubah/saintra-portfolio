# قواعد وإرشادات التعامل مع Git & GitLab (Git & GitLab Workflow Rules)

تحدد هذه الوثيقة القواعد والمعايير المعتمدة للتعامل مع مستودع الكود (Git & GitLab) لمشروع **SAINTRA Public Portfolio** لضمان استقرار التطبيق وسهولة الصيانة والتطوير المستقبلي.

---

## 1. هيكلية الفروع الأساسية (Branching Strategy)

### 🟢 `main` (Production Branch)
* **الوصف**: الفرع المستقر النهائي الخالي من الأخطاء والجاهز للنشر على بيئة الإنتاج المباشرة (Production).
* **الضوابط**:
  - فرع محمي (Protected Branch) على GitLab.
  - لا يجوز التعديل عليه أو الرفع المباشر إليه (`git push`) إلا للإصدارات المعتمدة.
  - يتم التحديث عليه حصراً عبر طلبات الدمج (Merge Requests) القادمة من فرع `dev` بعد اختبارها والتحقق منها.

### 🟡 `dev` (Development Integration Branch)
* **الوصف**: الفرع الرئيسي المخصص للتطوير والتكامل والربط اليومي بين المهام والميزات.
* **الضوابط**:
  - تعتبر البيئة المعتمدة لتجميع الميزات قبل إطلاقها إلى `main`.
  - يتم إنشاء الفروع الفرعية (Feature/Fix Branches) انطلاقاً منه.
  - يتم الدمج إليه بعد الاختبار البشري والمحلي التام للميزات والتعديلات.

---

## 2. سياسة الفروع الفرعية للعمليات والميزات (Feature & Fix Branches)

لكل عملية صيانة، تحديث، أو إضافة ميزة جديدة، يجب إنشاء فرع منفصل وتسميته بوضوح وفق النمط التالي:

* **الميزات الجديدة**: `feature/feature-name` (مثال: `feature/dark-mode-toggle`, `feature/blog-section`)
* **إصلاح الأخطاء**: `fix/bug-description` (مثال: `fix/contact-form-validation`, `fix/mobile-navbar`)
* **الصيانة والتحسين**: `maint/task-description` أو `refactor/task-description` (مثال: `maint/update-deps`, `refactor/data-shape`)
* **الوثائق**: `docs/doc-name` (مثال: `docs/git-rules`)

---

## 3. دورة حياة التطوير والدمج (Local Testing & Merge Workflow)

تطبيقاً لضابط **نفذ لوكال ونحضر كل شيء ثم نرفع رفع سريع للـ Remote** ونظراً لاستهلاك/انتهاء حصة الـ Pipeline في GitLab:

1. **إنشاء الفرع الفرعي انطلاقاً من `dev`**:
   ```bash
   git checkout dev
   git pull origin dev
   git checkout -b feature/your-feature-name
   ```

2. **التنفيذ والاختبار المحلي (Local Verification & Human Testing)**:
   - قم بكتابة الكود واختباره بشرياً في بيئة التطوير المحلية (`npm run dev`).
   - قم بتشغيل بناء الإنتاج محلياً للتأكد من عدم وجود أي أخطاء تجميع:
     ```bash
     npm run build
     ```
   - تحقق من العمل على جميع الشاشات والأجهزة واللغات قبل الاعتماد.

3. **حفظ التغييرات (Commits)**:
   - استخدم رسائل Commit واضحة ومباشرة تتبع المعايير القياسية:
     - `feat: إضافة ميزة جديدة`
     - `fix: إصلاح خلل في الواجهة`
     - `docs: تحديث الوثائق`
     - `refactor: إعادة هيكلة الكود دون تغيير السلوك`
     - `style: تحسينات التصميم والتنسيق`

4. **الدمج مع `dev` والتجهيز محلياً**:
   - بعد التأكد التام والاختبار البشري محلياً، قم بالانتقال إلى فرع `dev` ودمج التغييرات:
     ```bash
     git checkout dev
     git merge feature/your-feature-name
     ```

5. **الرفع السريع إلى Remote (`push`)**:
   - قم برفع الفرع المحدث سريعا إلى GitLab:
     ```bash
     git push origin dev
     ```
   - يمكنك حذف الفرع الفرعي المحلي بعد الدمج بنجاح:
     ```bash
     git branch -d feature/your-feature-name
     ```

---

## 4. ملخص القواعد الذهبية للعمل

1. **اختبر محلياً أولاً**: لا تقم برفع كود غير مجرب أو يحتوي على أخطاء بناء محلي.
2. **حافظ على فرع `main` نظيفاً**: كل كود موجود في `main` يجب أن يكون مستقراً ومجرباً 100%.
3. **التوثيق**: سجل أي تعديل جوهري في التقرير أو الوثائق المناسبة داخل مجلد `docs/`.
4. **رسائل Commit معبرة**: تجنب الرسائل المبهمة مثل "update" أو "fix".
